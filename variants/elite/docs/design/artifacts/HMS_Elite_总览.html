二、设计结构

一句话：对外是 Mem0 的皮（11 个同签名方法、同信封、同 filters、同 config dict），对内是 HMS 双平面。

State Index · 状态索引 search 只碰这一层

  • 每条记忆一个原子，七个轴：时间、有效期、实体、主题、角色、情绪、尺度
  • 原子里不存边；有效期是 SQL 条件，不是事后过滤
  • 三路召回 + 硬门 + 池内打分

Support Graph · 支持图 why / compile(deep) / 巩固碰这一层

  • 六类边：temporal · causal · revision · conflict · use · distill，每条边至少一个见证锚点
  • InterfaceEP = 低层子图的接口（支撑、边界、不变量、残差）
  • coarsen / project / refine，后台巩固四阶段
无见证无意义原子、边都指向源事件锚点（类型、DDL、写入路径三层强制）
原子不存边模块依赖上 mvmi/ 够不到 graph/，由 AST 扫描测试钉住

三、高光洞察：哪里起了作用，为什么

1多通道召回是准确率的地基，不是向量

同一哈希嵌入下，纯语义 hit@20 只有 10.8%，加上关键词、实体、时间门后 31.4%；换真实嵌入后 78.9%，与 mem0 的 milvus 混合检索（79.4%）持平，lines 契约下 84.3%。
这类问题都在问「谁、什么东西、什么时候」，答案是名字和实物，向量抓不住名字，关键词和实体通道抓得住。

2见证锚点让系统能离线复盘，直接换来了两次修 bug

每条记忆指向原话和记录下来的模型回复，所以能在零 API 费用下把三轮共 10,611 条真实抽取结果重放进库、逐项改动再看结果。compact 初版掉 7 个点的原因就是这么找到的：把模型的判定全改成 ADD，命中从 141 回到 154，其它改动全是零。
记忆系统的错误通常发生在写入时，没有见证就只能猜。

3「校验不过就整条作废」是首轮丢掉 31% 窗口的全部原因

模型在 attributed_to 里写了说话人名字，pydantic 只认 user / assistant，一批 208 条观察被丢。改成「规整而不拒绝」后三轮回放 0 拒绝。
LLM 面向的每个字段都会被填出意料之外的值，校验门应该把值归位，不该扔数据。

4钱和时间都花在输出 token 上，换输出格式比换模型有效

输出 ¥4 / 百万，缓存命中的输入 ¥0.02 / 百万，差 200 倍；JSON 信封的开销是内容的 2–4 倍。观察改成文本行后：¥11.56 → ¥2.24，每批 14.9 s → 3.8 s；模型不用为每条付格式开销，反而多写了陈述（1.75 → 2.68 条/窗口），召回率升到 84.3%。
早期用 JSON 是照 Mem0 的工程做的，当时没有成本模型；检索只读文本，字段是白付的钱。

5提示词里一句判定措辞，比 17 个字段加起来影响都大

compact 初版让模型把第 i 条观察和第 i 条候选配对判「重复」，1,685 个 NONE，22% 的陈述没入库。重写措辞并加相似度守卫后 NONE 回到 15–20 个。
模型照着示例的形状填：示例里观察 0 对候选 0，它就按位置配。

6记忆碎了，读侧要重组，状态卡片就是干这个的

full 契约下记忆行和状态卡片持平（61.3 / 61.8）；lines 契约下记忆行 54.9%、状态卡片 63.2%。
lines 写出更多更短的陈述，20 条短句堆给阅读器会选错（有据答错 55 → 72）；compile 按「有效事实 / 约束 / 证据」重组后反而更准。这是双平面里编译层的价值第一次在数字上出现。

7什么没起作用，同样重要

实体字段、类型字段、when 字段、主题标签对检索命中的影响为零（回放逐项验证）；批次从 25 缩到 12 也没用。
检索只读文本 token 和向量，这些字段只在编译和过滤时被用到。

8还没解决的三件事

记忆行上下文不带时间戳，10 道「几小时前」类的题答不了；英文入库、中文提问，「樱桃小丸子」变成 Chibi Maruko-chan 后三路都够不到；lines 契约下库体积 72.5 MB，是 mem0 的 5.6 倍。
前两件是上下文形状和入库语言的问题，读侧回放就能做 A/B；第三件要在产品化前定归档策略。
