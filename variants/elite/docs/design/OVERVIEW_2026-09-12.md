# HMS Elite 总览：脉络图、设计结构、高光洞察（2026-09-12）

三部分：一条消息怎么变成记忆、一次提问怎么取回记忆（脉络图，标了三种抽取契约的实测数字）；系统由哪几块组成（设计结构）；这一版里到底是哪些设计起了作用、为什么（高光洞察，说人话）。所有数字来自 2026-09-11/12 的真实 deepseek-flash 运行（EgoLife 204 题、4,851 个转写窗口）与零 API 回放，来源见文末。

## 一、脉络图

### 写入：`HMS.add(messages)`

```
 消息进来
   │
   ▼
 ① 入口：规范化、剥离保留键                         本地 <1 ms
   │
   ▼
 ② Txn A（持锁）：原话 + sha256 见证锚点先落库          本地 1–2 ms  ← 从这一刻起原话不会丢
   │
   ▼  锁外
 ③ 分段（≤400 字符）+ 邻域候选（向量最近 10 条 + 最近 10 条事件）   本地，毫秒级
   │
   ▼
 ④ LLM 抽取（唯一付费环节，一次往返）
      full    JSON 17 字段   每窗口 561 入 / 495 出 token   每批 14.9 s   ¥11.56 / 204 题
      compact JSON 9 键      每窗口 336 入 / 157 出         每批  7.3 s   ¥4.35
      lines   文本行         每窗口 343 入 /  51 出         每批  3.8 s   ¥2.24   （mem0：657 / 45，3.5 s，¥1.98）
   │
   ▼
 ⑤ 规整而不拒绝 + 本地推导七轴（主语、谓词、关系、情绪、主题、实体、说话人→actor_id）   每条 <0.1 ms
   │
 ⑥ 判定守卫：NONE / REVISE 只在新旧文本相似时生效，否则 ADD                            每条 <0.1 ms
   │
   ▼
 ⑦ 嵌入（fastembed 384 维，本地）                       每批约 78 ms
   │
   ▼
 ⑧ Txn B（持锁）：原子 + 七轴 + 修订/冲突/时间/使用边 + FTS + 向量索引    每批约 230 ms
   │
   ▼
 状态存储（SQLite 22 表 + FTS5 + 向量；可换 Milvus）    每条原子约 6.5 KB
```

写入一条记忆的账（空闲价）：批量摊销 lines ¥0.00017 / compact ¥0.00056 / full ¥0.00136；单条即时写 2.4 s、¥0.0025（几乎全是模型往返）。

### 读取：`HMS.search(query)` → 上下文 → 回答

```
 提问
   │
   ▼
 ① 查询嵌入                                              本地 3.8 ms
   │
   ▼
 ② 有界多通道召回：语义 ANN + FTS5 关键词 + 实体（各取 K）+ 条件启用的近因；硬门（用户、有效期、尺度）下推 SQL
    池内按 1.0 / 0.5 / 0.5 / 0.25 / 0.25 加权，半衰期 30 天，取 top-20        ①+② 合计中位 10–11 ms，P95 28 ms，¥0
   │
   ├─▶ ③a 记忆行上下文：20 条 text（≈330 token）
   │
   └─▶ ③b 状态卡片上下文：compile() 按槽位重组（当前目标 / 有效事实 / 失效假设 / 约束 / 下一步 / 证据，≈1,600 token）
   │
   ▼
 ④ 回答 LLM（可选，产品侧）                               0.6–0.8 s，¥0.0003–0.0016 / 题
```

准确率（204 题，deepseek-flash 四选一）：

| 读侧 | full | compact | lines | mem0 |
|---|---|---|---|---|
| 记忆行 | 61.3% | 56.4% | 54.9% | 56.9% |
| 状态卡片 | 61.8% | 62.7% | **63.2%** | — |
| hit@20 | 78.9% | 77.9% | **84.3%** | 79.4% |

## 二、设计结构

**一句话**：对外是 Mem0 的皮（11 个同签名方法、同信封、同 filters、同 config dict），对内是 HMS 双平面。

**两个平面**

- State Index（状态索引）：每条记忆一个原子，七个轴（时间、有效期、实体、主题、角色、情绪、尺度），原子里不存边。`search` 只碰这一层。
- Support Graph（支持图）：六类边（temporal / causal / revision / conflict / use / distill），每条边至少一个见证锚点；InterfaceEP 是低层子图的接口（支撑、边界、不变量、残差）。`why`、`compile(deep)`、后台巩固碰这一层。

**四条不变量，三层强制（类型、DDL、写入路径）**

1. 无见证无意义：原子、边都指向源事件的锚点。
2. 原子不存边：模块依赖上 `mvmi/` 够不到 `graph/`。
3. 修订代替删除：`BEFORE DELETE / UPDATE` 触发器拒绝物理删改，旧版本归档。
4. 高层是接口：InterfaceEP 必须有支撑节点，边界边带见证。

**八个模块组，依赖无环（由 AST 扫描测试强制）**

| 组 | 目录 | 职责 |
|---|---|---|
| A 基础 | models / enums / configs / utils / memory.schema, storage | 类型、22 表 DDL、StateStore、提示词契约 |
| B 提供者 | llms / embeddings / index / entities / reranker | RuleLLM、deepseek、ollama、fastembed、哈希、sqlite、milvus、spaCy |
| C 摄取 | ingest/ | 事件、锚点、抽取（三种契约）、推导、判定守卫、原子物化 |
| D 索引 | mvmi/ · utils/scoring | 过滤 DSL、查询规划、多通道召回、五信号融合 |
| E 图 | graph/ | 节点边见证、coarsen / project / refine、溯因 |
| F 编译 | compiler/ | 六槽 ContextIR、工作状态卡、覆盖度选择 |
| G 运维 | ops/ · daemon · runtime | 反馈、检查点、交接、巩固四阶段、守护线程 |
| H 门面 | memory/main · async_main · server · cli · hms4eye | HMS 40 方法、AsyncHMS 镜像、FastAPI、hms4eye 7 方法适配 |

**三种抽取契约**（`ingest.extraction_output`，默认 `full`；2026-09-18 默认改为 `lines`，读侧 `HMS.context()`（会话卡前缀 + 带时间戳记忆行，READER_AB_2026-09-18.md，变更记录第 108 行））

| | LLM 写什么 | 库端推导 | 适合 |
|---|---|---|---|
| full | 17 字段 JSON | 无 | 读侧直接喂记忆行、要最高准确率 |
| compact | 9 键 JSON | 主谓宾、关系、情绪、主题、置信度 | 折中 |
| lines | 文本行，EP / 判定段仅在出现时写 | 同 compact | 成本敏感、读侧走状态卡片 |

**接口面**：Mem0 兼容 11 个；HMS 原生 17 个（compile、why、handoff、feedback、checkpoint、rollback、consolidate…）；StateAPI 12 个业务状态委托；hms4eye 7 方法适配器（点亮对方 33 个 no-op 中的 13 个）。

## 三、高光洞察：哪里起了作用，为什么

**1. 多通道召回是准确率的地基，不是向量。**
同一哈希嵌入下，纯语义 hit@20 只有 10.8%，加上关键词、实体、时间门后 31.4%；换成真实嵌入后 78.9%，与 mem0 的 milvus 混合检索（79.4%）持平，lines 契约下 84.3%。为什么：这类问题都在问「谁、什么东西、什么时候」，答案是名字和实物，向量抓不住名字，关键词和实体通道抓得住。

**2. 见证锚点让系统可以离线复盘，这一点直接换来了两次修 bug。**
每条记忆都指向原话和记录下来的模型回复，所以可以在零 API 费用下把三轮共 10,611 条真实抽取结果重放进库、逐项改动再看结果。compact 初版掉 7 个点的原因就是这样找到的：把模型的判定全改成 ADD，命中从 141 回到 154，其它改动全是零。为什么重要：记忆系统的错误通常发生在写入时，没有见证就只能猜。

**3. 「校验不过就整条作废」是首轮丢掉 31% 窗口的全部原因。**
模型在 `attributed_to` 里写了说话人名字，pydantic 只认 user / assistant，一批 208 条观察被丢。改成「规整而不拒绝」后三轮回放 0 拒绝。为什么：LLM 面向的每个字段都会被填出意料之外的值，校验门应该把值归位，不该扔数据。

**4. 钱和时间都花在输出 token 上，所以换输出格式比换模型有效。**
输出 ¥4 / 百万，缓存命中的输入 ¥0.02 / 百万，差 200 倍。JSON 信封的开销是内容的 2–4 倍。把观察改成文本行后：费用 ¥11.56 → ¥2.24，每批 14.9 s → 3.8 s，而且模型不用为每条付格式开销，反而多写了陈述（1.75 → 2.68 条/窗口），召回率升到 84.3%。为什么早期用 JSON：照 Mem0 的工程做，且当时没有成本模型。

**5. 提示词里一句判定措辞，比 17 个字段加起来影响都大。**
compact 初版让模型把第 i 条观察和第 i 条候选配对判「重复」，1,685 个 NONE，22% 的陈述没入库。重写措辞并加上相似度守卫后 NONE 回到 15–20 个。为什么：模型会照着示例的形状填，示例里观察 0 对候选 0，它就按位置配。

**6. 记忆碎了，读侧要重组，状态卡片就是干这个的。**
full 契约下记忆行和状态卡片持平（61.3 / 61.8）；lines 契约下记忆行 54.9%、状态卡片 63.2%。为什么：lines 写出更多更短的陈述，20 条短句堆给阅读器会选错（有据答错 55 → 72），`compile` 按「有效事实 / 约束 / 证据」重组后阅读器反而更准。这也是双平面里编译层的价值第一次在数字上出现。2026-09-18 的读侧 A/B（`READER_AB_2026-09-18.md`）证实：去重与时间排序不解释这个差异（52.9%），卡片对记忆行 +22 题、p=0.001；预算 1200→400 单调退回记忆行水平；「会话卡前缀 + 带时间戳记忆行后缀」70.1%，是目前最准的读法；实测每题 ¥0.00072 依赖 15 分钟前另一变体预热的同一前缀，冷前缀重算 ¥0.00185，高于卡片 1200 的 ¥0.00156。

**7. 什么没起作用，同样重要。**
实体字段、类型字段、when 字段、主题标签对检索命中的影响为零（回放逐项验证）；批次从 25 缩到 12 也没用。为什么：检索只读文本 token 和向量，这些字段只在编译和过滤时被用到。

**8. 还没解决的三件事。**
记忆行上下文不带时间戳，10 道「几小时前」类的题答不了；英文入库、中文提问，「樱桃小丸子」变成 Chibi Maruko-chan 后三路都够不到；lines 契约下库体积 72.5 MB，是 mem0 的 5.6 倍，归档策略要在产品化前定。
